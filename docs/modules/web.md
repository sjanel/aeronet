# JavaScript pages

!!! warning "Experimental"
    The web module is experimental: its API and behavior may change in a minor release, and the scripts of real
    sites may use Web APIs that it does not have yet (see [Limitations](#limitations)).

The web module loads pages the way a browser does without rendering them: `WebClient::navigate()` fetches a document, parses it, runs its scripts over a DOM of the document, follows the navigations they start, and returns the page as its scripts left it. It reads the pages whose content is produced, or only reached, through JavaScript: a waiting room that sends every visitor through a script, a page that builds its table from embedded data. Many pages need none of it: see [Pages built by JavaScript](html.md#pages-built-by-javascript) first, as an `HtmlDocument` costs no script run.

The scripts run on [QuickJS-ng](https://github.com/quickjs-ng/quickjs) (MIT, ES2023 and later), in the process. The `AERONET_ENABLE_JS` CMake option enables the module: `ON` by default when aeronet is the main project, `OFF` when it is a subproject, and always `OFF` without `AERONET_ENABLE_HTML` (the documents are [HtmlDocument](html.md)s) and `AERONET_ENABLE_HTTP_CLIENT`. An installed QuickJS-ng (its `qjs` CMake package) is used when found (Release builds, vcpkg feature `js`), otherwise QuickJS-ng is downloaded and built as a static library, without its `quickjs-libc` module: a commit of its master after 0.18.0 (`d06a85c1`), for the fixes that [modules](#modules) need. The Conan package does not have the module: QuickJS-ng is not in Conan Center.

## Load a page

```cpp
#include <aeronet/html-element.hpp>
#include <aeronet/web-client.hpp>

#include <chrono>
#include <string>

WebClient web;  // its cookies and storage outlive navigate()

// Until the data is in the document: checked before the scripts run, then after each of them.
auto page = web.navigate("https://shop.example/product/42",
                         {.untilSelector = "script#__NEXT_DATA__", .timeout = std::chrono::seconds{10}});
if (page) {
  if (const HtmlElement data = page->document().querySelector("script#__NEXT_DATA__")) {
    const std::string json = data.textContent();  // parse it with glaze
  }
  // The final URL, after the redirects and the navigations of the scripts.
  const std::string url(page->url());
  // Any expression, its value as JSON text.
  auto title = page->evaluate("document.title");
}
```

`navigate()` returns a `std::expected<WebPage, WebErrc>`. It fails only when the URL, or the URL of a navigation of a page, is not an http or https URL that the HTTP client can request (`invalidUrl`: not http or https, with user info, or port 0), when the request of a document fails (`requestFailed`, logged with the `HttpClientErrc` of the failure), when the server of a document is less public than allowed (`addressBlocked`, see [Local network access](#local-network-access)), or when the pages start more navigations than `WebClientConfig::maxNavigations` (`tooManyNavigations`). A page is returned whatever its status code (`WebPage::status()`), as browsers show error pages, and whatever its scripts throw: the exceptions that no script caught are in `WebPage::uncaughtErrors()` (the first 100, each cut after 8 KiB, as views valid as long as the page). It throws `std::invalid_argument` for an invalid `untilSelector`, and `std::bad_alloc` (or `std::runtime_error` for a `maxScriptMemory` too small to set up a page) on memory exhaustion.

A `WebPage` holds its document and its JavaScript runtime: `document()` is the [HtmlDocument API](html.md) on the tree that the scripts modified, and the C++ changes made to it are seen by the next scripts. A page refers to its `WebClient` (cookies, storage): it must not outlive it, and the client cannot move while it has pages (a move, or an assignment to it, throws `std::logic_error`). Neither is thread-safe.

The [web-page example](../../examples/web-page.cpp) (binary `aeronet-web-page`) reads the price and the stock of a product of the Nintendo Store this way. The store sends each new visitor to a waiting room (Queue-it), whose page checks the cookies with a script, then navigates back to the store with a signed token: `navigate()` follows that path, then stops on `script#__NEXT_DATA__` before any script of the product page runs, and glaze reads the fields it needs from the 600 KB of JSON (about 500 ms in all). Given a period, it loads the page again until the product can be ordered: the client keeps the cookie of the waiting room, so the next loads go straight to the product page (about 60 ms).

## How a page loads

`navigate()` stops at the first of three conditions, given by `WebPage::stopReason()`:

| `StopReason` | Condition |
| --- | --- |
| `SelectorMatched` | An element matches `NavigateOptions::untilSelector`: checked once the document is parsed, before any script runs, then after each task that changed the document |
| `StateReached` | The page reached `NavigateOptions::until`: `LoadState::DomContentLoaded`, `Load` (the default), or `NetworkIdle` (no timer nor request left) |
| `TimedOut` | `NavigateOptions::timeout` (10 s by default) ran out, for the whole navigation: a running script is stopped, the page is returned as it is |

The document is parsed whole, in scripting mode (the contents of `<noscript>` are text, as in browsers that run scripts), then its scripts run in the order of a browser, each one a task:

1. the parser-blocking scripts, inline or external (`src`), in document order, `document.readyState` being `"loading"`;
2. `readyState` becomes `"interactive"` (`readystatechange`), the `defer` scripts and the [module scripts](#modules) run in document order, then `DOMContentLoaded` is dispatched on the document: `LoadState::DomContentLoaded` stops there;
3. the `async` scripts run (classic or module), `readyState` becomes `"complete"` (`readystatechange`) and `load` is dispatched on the window: `LoadState::Load` stops there;
4. with `LoadState::NetworkIdle`, the timers and the requests of the scripts run until none is left (see [Timers](#timers) and [Requests of the scripts](#requests-of-the-scripts)).

After each task, the microtasks run (promise reactions, `queueMicrotask()`), the unhandled promise rejections are reported, then the stop conditions and the navigations are checked. Between the tasks, the timers due at once run, then the requests of the scripts are sent, each response a task. Classic scripts and module scripts run: a `type` other than a JavaScript MIME type or `module` (`application/json`, `importmap`...) is a data block, and the `nomodule` classic scripts do not run, as in a browser with modules. An external script is fetched with the HTTP client of the page, one at a time, as a subresource of its document (its `Referer`, and the cookies of [Cookies and storage](#cookies-and-storage); a `crossorigin` attribute other than `use-credentials` sends cookies only to the origin of the document): a failed request (or a status other than 2xx, or an empty `src`) skips it and dispatches `error` on its element, a loaded one dispatches `load`, which does not reach the window. Its bytes are decoded as browsers do: the encoding of its byte order mark, else of the `charset` of its `Content-Type`, else of its `charset` attribute, else of its document, invalid sequences becoming U+FFFD. The scripts of a document stop at `WebClientConfig::maxScriptBytes`.

A script element that a script creates (`document.createElement('script')`, or a copy of such an element not run yet, also inside a deep copy) runs once inserted in the document, as in browsers: an inline one at once, inside the insertion call (`appendChild()`, `append()`, `insertBefore()`...), with `document.currentScript` set to it, its errors reported without reaching the inserting script; an external one is fetched and run as a task, between the tasks (before `load` when inserted while the document loads), then dispatches `load` or `error` on its element. Its URL, `charset` and `crossorigin` are read when it is inserted: changing them later does not change what runs. This is how bundlers load their chunks (webpack). An element inserted without text nor `src` runs when it gets one of them (its `text`, `textContent`, `innerHTML`, a child, an adjacent text or HTML inside it, the `data` of its text). Each script runs once, and those of an HTML fragment (`innerHTML`, `insertAdjacentHTML()`) never run, nor the inserted ones of a type other than a classic or module script. An inserted module script, inline or external, runs as a task, its code or URL read when it is inserted. Until it runs, an inserted script that waits for its task holds a copy of its URL or code, counted in the native memory of the page (`maxScriptMemory`): beyond it, the insertion throws an out of memory error. An inline script inserted by a parser script writes after it with `document.write()`, the external ones cannot write. An inline script stopped by the deadline stops the script that inserted it too, as the deadline cannot be caught.

A script sees the whole document, already parsed: a browser parsing a slow network stream would show it only the elements before it. `document.write()` during a script inserts its output after the script once it ends, and the scripts it writes run right after it; elsewhere (timers, events, modules, `evaluate()`) it is ignored.

## Modules

The ES modules need two fixes of QuickJS-ng that no release has yet (the latest, 0.18.0, writes into a freed module when a page is freed while one of its modules awaits): the downloaded QuickJS-ng has them, and an installed one is assumed to have them from 0.19.0 on, the first release expected after them. With an older installed one (the vcpkg port has 0.16.2), the pages run as in a browser without modules: the module scripts are skipped, the `nomodule` ones run, and `import()` rejects.

The ES modules run as in browsers: the module scripts (`<script type="module">`, inline or with a `src`), their `import` declarations, `import()` from any script (classic, module, timer, `evaluate()`), and `import.meta` (`url`, and `resolve()`, which gives the URL of a specifier). A module script is deferred, unless `async`, and runs with the module semantics: strict mode, `this` undefined, no `document.currentScript`, top-level `await` (the next scripts do not wait for it).

A module graph loads before any of its modules runs. Each module is fetched with the HTTP client of the page, one at a time, when the import that needs it is compiled: the network takes no time on the virtual clock, and an `import()` resolves within the microtasks of its task. The requests are those of the `cors` mode, as subresources of the document, with the `Referer` of the default policy of the browsers (`strict-origin-when-cross-origin`) from the base URL of the importing module (from the document for a module script, an inline script and `evaluate()`): a module of another origin needs the consent of its server (`Access-Control-Allow-Origin`), and cookies go only to the origin of the document, unless the module script has `crossorigin="use-credentials"` (its imports too; `import()` uses the default). A response must be a success with a JavaScript MIME type (`text/javascript`...), decoded as UTF-8; a redirect is followed with the rules of [the requests of the scripts](#requests-of-the-scripts), and the imports of the module resolve against its final URL.

A specifier is an absolute URL, or a URL starting with `/`, `./` or `../`, resolved against the URL of the importing module, or against the base URL of the document for an inline script and `evaluate()`. A bare specifier (`"react"`) needs an import map, which aeronet does not have: it fails with a `TypeError`. A module is loaded once per page, by its URL (its fragment included): every import of that URL shares it.

A graph that fails does not run at all:

- a module that cannot be fetched (network error, status, MIME type, CORS, a URL other than http and https) dispatches `error` on the module script, and nothing is reported, as for a classic script;
- a module that does not compile (a `SyntaxError`, also for an import attribute other than `type`; a JSON or CSS module: `with { type: 'json' }` throws a `TypeError`) or whose import does not exist in its module (a link error) is reported in `WebPage::uncaughtErrors()`, and an external module script still dispatches `load`;
- `import()` rejects with that error, a `TypeError` for a module that cannot be fetched.

An error thrown by a module as it runs is reported, also after a top-level `await`. A module that failed fails again for the next imports of its URL with the same error, without request, as does each module of its graph that reaches it, also through a cycle: none of them runs. The deadline (or a memory exhaustion) stopping a graph while it loads leaves the modules of the graph already compiled failed for good, with a `TypeError` that the scripts can catch, as QuickJS-ng keeps them with the import that could not load; the modules not compiled yet load again for a later import. The requests of the modules count toward `WebClientConfig::maxRequests`, but those of the module scripts of the parser (as their classic external scripts), and their code toward `maxScriptBytes`; the [script cache](#performance) keeps their bytecode too. Each level of imports compiles its module inside the one above, on the native stack: an import chain deeper than `maxScriptStackSize` allows (between 200 and 300 modules with the default 1 MiB in a debug build, about 4 KiB per level, more in a release build) fails with a `RangeError`. A memory exhaustion of the JavaScript heap while a graph loads stops the loading of modules in the page for good (each next one fails with a `TypeError`), as QuickJS-ng does not undo a failed resolution.

## Timers

`setTimeout()`, `setInterval()`, `requestAnimationFrame()` (16 ms) and `requestIdleCallback()` run on a virtual clock: nothing sleeps. While the document loads, the clock stays at 0, so only the timers due at once run, between the tasks. With `LoadState::NetworkIdle`, after `load`, the clock jumps from timer to timer, in the order of their due times, until none is left. A navigation over a minute of timers takes milliseconds.

Bounds keep endless timers finite: a timer due later than `WebClientConfig::maxTimerDelay` (1 minute) after the start of the document never runs, an interval is cleared after `maxIntervalRuns` (100) runs, and beyond 5 nested levels a timer waits at least 4 ms, as in browsers, so that a `setTimeout(f, 0)` chain moves the clock, also through the microtasks of a timer (`await new Promise(r => setTimeout(r))` in a loop). `Date.now()` and `performance.now()` give the real time.

## Navigations

A script navigates by assigning `location.href`, `window.location`, `document.location`, `location.search` or `location.pathname`, by calling `location.assign()`, `replace()` or `reload()`; a document navigates with `<meta http-equiv="refresh">`. The current task ends first (the last navigation of a task wins), then the page and its runtime are dropped and the new URL, resolved against the base URL of the document (`<base href>`), is loaded with the same options, until the deadline of the first `navigate()` call. A refresh with no delay is followed after `load`; a delayed one only with `NetworkIdle`, after the timers due before it, within `maxTimerDelay`. A refresh of the page itself, and a navigation to a URL other than http and https (`javascript:`, `mailto:`), are not followed, and a page of the Internet cannot navigate to the host nor to its local network (see [Local network access](#local-network-access)). A navigation to a fragment of the document only changes its URL, as does `history.pushState()` (same origin only).

Each navigation counts toward `maxNavigations` (20), beyond which `navigate()` fails: a page that reloads itself forever is an error, not a timeout. The HTTP redirects are followed by the HTTP client and count toward its `maxRedirects` instead. `WebPage::url()` is the final URL of the document, with the fragment of the last redirect whose `Location` has one, else of the URL that was asked for (RFC 9110 §10.2.2).

## Requests of the scripts

`fetch()`, `XMLHttpRequest` and `navigator.sendBeacon()` send their requests with the HTTP client of the page. The network takes no time on the virtual clock: a request is sent between the tasks, after the timers due at once, in the order the scripts made them, and its response is a task, whose callbacks and promise reactions run with their microtasks. A request made while the document loads gets its response before `load` (before `DOMContentLoaded` if made by a parser-blocking script), and those made later, by the timers or by the responses, run until the network is idle with `LoadState::NetworkIdle`. A synchronous `XMLHttpRequest` (`open(method, url, false)`) is sent at once, during its script. An `AbortController` cancels a request not sent yet.

```cpp
#include <aeronet/html-element.hpp>
#include <aeronet/web-client.hpp>

#include <chrono>
#include <string>

WebClient web;
// A single-page app that renders its table from an API: loaded until no timer nor request is left.
auto app = web.navigate("https://app.example/fees", {.untilSelector = "table tr", .until = LoadState::NetworkIdle,
                                                     .timeout = std::chrono::seconds{10}});
if (app && app->stopReason() == StopReason::SelectorMatched) {
  for (const HtmlElement row : app->document().querySelectorAll("table tr")) {
    const std::string text = row.textContent();
  }
}
```

The requests follow the rules of the Fetch Standard:

- **Headers**: the script cannot set the headers that the browser sets (`Host`, `Cookie`, `Origin`, `Referer`, `Content-Length`, the `Sec-` and `Proxy-` ones...): they are ignored. `Accept` is `*/*` unless the script sets one, the `User-Agent` and `Accept-Language` are those of the HTTP client, and the `Referer` follows the default policy of the browsers, `strict-origin-when-cross-origin`: the URL of the document for its own origin, its origin for another one, none from https to http.
- **Credentials**: `credentials: 'same-origin'` (the default of `fetch()`, and of `XMLHttpRequest` without `withCredentials`) sends and stores cookies only while the URL stays of the origin of the document, `'include'` always, `'omit'` never.
- **CORS**: a script reads a response of another origin only if its server consents. In the default `cors` mode, the request carries an `Origin`, and its response needs an `Access-Control-Allow-Origin` of that origin (or `*` without credentials, `Access-Control-Allow-Credentials: true` with them), else it is a network error (a `TypeError` for `fetch()`, an `error` event for `XMLHttpRequest`). A request that a form could not send (a method other than `GET`, `HEAD` and `POST`, a header other than `Accept`, `Accept-Language`, `Content-Language`, a form `Content-Type` and a simple `Range`) is first preflighted with an `OPTIONS` request, which must allow its method and headers (`Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`). The response of another origin shows only the safelisted headers (`Content-Type`, `Content-Length`, `Cache-Control`...) and those of its `Access-Control-Expose-Headers`; `Set-Cookie` never shows. The `no-cors` mode gets an opaque response (status 0, no header, empty body), the `same-origin` mode fails for another origin.
- **Redirects**: each redirect is checked as by browsers before it is followed: the `same-origin` mode fails before a request to another origin, a redirect response of another origin needs the consent of its server (in the `cors` mode), the `Origin` and the `Referer` are those of the new URL (the `Origin` becomes `null` after a redirect from another origin to a third one), and a request that needs a preflight at its new URL gets one there, with the method that the redirect gives it. A preflight is never redirected. The redirects of a request are bounded by `HttpClientConfig::maxRedirects`: a redirect not followed (beyond them, or from https to http) is a network error.
- **Address spaces**: a page reaches only the servers of its address space and of the more public ones, see [Local network access](#local-network-access).
- **Limits**: a document makes at most `WebClientConfig::maxRequests` (1000) requests, the external scripts that its scripts insert included, the next ones fail as network errors (an `error` event for an asynchronous `XMLHttpRequest`, as for a URL other than http and https); each response is bounded by `HttpClientConfig::maxResponseBytes`, and its body is held in the JavaScript heap of the page: a response that does not fit in it is a network error. A request already sent can exceed the deadline of `navigate()` by up to the `requestTimeout` of the HTTP client.
- **Methods**: those of `HttpRequest` (`GET`, `HEAD`, `POST`, `PUT`, `DELETE`, `OPTIONS`, `PATCH`), in upper case: another one is refused with a `TypeError`, also a lower-case spelling that `fetch()` does not normalize (`'patch'`), which browsers send as is.

A response body is read whole: `Response.body` is `null` (no streams), `blob()` and `formData()` are not supported, and the bodies are strings, `URLSearchParams`, `ArrayBuffer` and its views (another object becomes its string). The bodies of `fetch()` are decoded as UTF-8 (`text()`, `json()`), whatever their `Content-Type`; `XMLHttpRequest` decodes `responseText` with the charset of the response (or of `overrideMimeType()`), its `json` as UTF-8, and has the `''`, `text`, `json` and `arraybuffer` response types. The `redirect`, `cache` and `integrity` options, and the `timeout` of `XMLHttpRequest`, have no effect.

## Cookies and storage

The `HttpClient` of a `WebClient` (`httpClient()`) always has its cookie jar enabled: the cookies set by the responses and by `document.cookie` live as long as the client, across sites and `navigate()` calls, and go with the next requests, as in the [HTTP client](http-client.md#cookies). `document.cookie` is the non-HTTP API of RFC 6265bis: the `HttpOnly` cookies are hidden from the scripts, which cannot create, replace or delete one.

The requests of a document (its scripts, `fetch()`, `XMLHttpRequest`) are those of its site for the `SameSite` cookies (RFC 6265bis §5.2): a request to another site, or redirected through one, sends no `SameSite=Strict` or `Lax` cookie, and its response stores none. The navigations are their own site, as with the HTTP client: after a redirect to another site, only the `SameSite=Strict` cookies are withheld (and the `Lax` ones for an unsafe method). `HttpClient::requestUpdating()` takes these rules as a `PageRequestContext`: the URL of the document of a request, its credentials mode, the address space of what makes it, and a hook that decides, before each redirect, whether it is followed (a chain stopped there continues with the next call). These requests never use the response cache of the HTTP client (`HttpClientConfig::cache`): a cached response tells neither the URL it came from nor the cookies of the page it was received for.

`localStorage` and `sessionStorage` are kept in memory per origin, as long as the client: a page reads what an earlier page of its origin stored, also from an earlier `navigate()` call. An origin stores at most 5 MiB per storage (`QuotaExceededError` beyond).

## Evaluate a script

`WebPage::evaluate(script, timeout)` runs `script` as a classic script in the page (which can `import()` modules), then its microtasks, and returns its completion value as JSON text (`JSON.stringify`): `"\"text\""`, `"42"`, `"{\"a\":1}"`, or an empty string for a value without JSON representation (`undefined`, a function). It fails with the text of the exception the script throws, also when it runs longer than `timeout` (10 s by default). The timers it sets never run, the requests it makes are not sent (but a synchronous `XMLHttpRequest`) and the navigations it starts are ignored.

## Configuration

`WebClient(WebClientConfig)` takes the configuration of its HTTP client and the limits of its pages, listed in the [client configuration reference](../reference/client-configuration.md#javascript-pages): JavaScript heap (256 MiB), native stack (1 MiB), script bytes per document (32 MiB), timer horizon, interval runs, requests per document, navigations, the size of the script cache, and the address space of the application (see [Local network access](#local-network-access)). A memory allocation beyond the heap limit throws an out of memory error in the script, a deeper recursion than the stack limit a `RangeError`. The stack limit must stay below the free stack of the calling thread, or a deep recursion crashes the process: the main thread of a Windows executable has 1 MiB by default, link it with a larger stack (`/STACK:8388608`, as QuickJS-ng does for its own executables) or lower the limit. A JavaScript call takes much more native stack in unoptimized builds (about 9 KiB, 70 KiB with the sanitizers) than in release builds. The native memory that the scripts make a page hold is bounded apart by the same limit: the nodes and attributes they add (about 200 bytes each with their text, an HTML fragment is first checked as 32 bytes per byte), the output of `document.write()` until it is parsed, their pending timers, the URL or code of the inserted scripts waiting for their task. A replaced value or a removed attribute gives its memory back; a removed node does not, as it stays in the document. With `maxScriptMemory` at 256 MiB, a page cannot add more than about 1.4 million nodes.

## Security

The scripts of the pages run in the process. They have no file, network or process access other than the requests of their page, their memory, stack and time are bounded, and `SharedArrayBuffer` and `Atomics`, the source of several memory-safety bugs of the engine, are removed. A bug of the engine can still be exploited by a hostile page: load untrusted sites from an unprivileged process. The ASAN CI legs build QuickJS-ng with the sanitizers too. The Web APIs written in JavaScript run among the scripts of the page, which can replace what they use (`Array.prototype.join()`, `Uint8Array`, the getters of `Request`...): that breaks these APIs for the page alone, as the native functions under them check their arguments.

### Local network access

A page of the Internet must not make the client send requests to the host itself nor to its local network: an administration interface on `localhost`, a router, the metadata service of a cloud machine (`169.254.169.254`). CORS does not prevent it, as it only stops the page from reading the response, not the request from being sent. As the Local Network Access of browsers, the client classifies each IP address in an address space (`AddressSpace`, from the most private): `Loopback` (127.0.0.0/8, ::1, 0.0.0.0...), `Local` (private-use, link-local, carrier-grade NAT, unique-local...) and `Public`, following the table of the [specification](https://wicg.github.io/local-network-access/#non-public-ip-address-blocks), plus the NAT64 addresses (`64:ff9b::/96`) as the IPv4 address they embed. Then:

- a page reaches only the servers of its address space and of the more public ones: the server of its document gives it its address space. That applies to the requests of its scripts (`fetch()`, `XMLHttpRequest`, `sendBeacon()`, the preflights), its external scripts and its navigations (`location`, `<meta http-equiv="refresh">`);
- each redirect leads only to the servers of the address space of the server that sent it and of the more public ones, so that a server cannot lead the client back either: a public site redirecting `navigate()` to `http://169.254.169.254/` fails with `WebErrc::addressBlocked`. A redirect of a script request that needs a new CORS preflight keeps that rule, for the preflight and the request after it;
- the URL given to `navigate()` reaches every server by default: the application chose it. `WebClientConfig::addressSpace` restricts it, `AddressSpace::Public` keeping `navigate()` on the Internet, for URLs given by untrusted users.

A request blocked so is never sent: the check is made on the addresses that the name resolves to, before connecting (a name resolving to a private address after the check of the application, as in a DNS rebinding attack, is still refused), and on the pooled connections. The requests of the scripts fail as network errors, and the documents with `WebErrc::addressBlocked`. Through a forward proxy, which resolves the names itself, only a URL whose host is an IP address or `localhost` tells the address space of a server: the other names are taken as public, and the proxy should refuse the private destinations itself. An IPv4 address in one of the short, octal or hexadecimal forms that browsers and `inet_aton()` read (`127.1`, `2130706433`, `0x7f.0.0.1`, `0177.0.0.1`) is that address, and a host ending in a number, or with a colon, that is not a valid address (`256.0.0.1`, `1.2.3.4.5`, `::ffff:127.1`) is taken as the host itself, as a proxy might still read it as an address. Unlike browsers, which check the redirects of a request against its page only, a redirect is checked against its server too: a page of the local network fetching a public server cannot be redirected back into the local network. `WebClientConfig::allowLessPublicRedirects` restores the rule of browsers, for the single sign-on of an intranet through a public identity provider (intranet, then public login page, then intranet): the redirects are then only checked against the page, and against `WebClientConfig::addressSpace` for the URL given to `navigate()`, whose redirects reach every server by default. `HttpClient::requestUpdating()` applies these rules from `PageRequestContext::addressSpace` (the address space of what makes the request) and reports the address space of the final server; the other requests of `HttpClient` reach every server.

## Performance

Measured by [web-page_bench.cpp](../../benchmarks/internal/web-page_bench.cpp) on a Release build (clang 23, x86-64 desktop, one core):

| Operation | Cost |
| --- | --- |
| Setup of a page (small document) | About 170 µs: QuickJS-ng runtime and context 45 µs, then the parsing, the bindings and the JavaScript part of the Web APIs, read back as bytecode (15 KB, 30 µs) |
| Setup of the first page of a `WebClient` | About 870 µs: it compiles the JavaScript part of the Web APIs, for the next pages |
| First use of the network and text APIs in a page | About 220 µs more, once: `fetch()`, `XMLHttpRequest`, `URL`, `TextEncoder`... are set up on the first use of one of them (28 KB of bytecode), so that a page without them does not pay for them, nor one that only replaces them (`window.fetch = ...`) |
| First use of the observers and media queries in a page | About 65 µs more, once (`matchMedia()`, `IntersectionObserver`, `getComputedStyle()`, `DOMRect`...) |
| First use of `Intl` in a page | About 250 µs more, once (`Intl`, `toLocaleString()` of the numbers and dates), then about 19 µs for a new `NumberFormat` and its first `format()` |
| `localeCompare()` of two ASCII strings | About 25 ns, native: the sorts do not set `Intl` up |
| Native DOM getter or method call | About 20 ns more than a loop iteration without the call |
| Lookup of a global that does not exist (feature detection) | About 23 ns more than a loop iteration without it, 65 ns for a name of the form `HTML...Element` |
| Move of a tree of 100 elements | About 160 ns, most of it lexbor visiting each node: the same while a script element created by a script waits for its insertion (the insertion checks those elements, not the tree) |
| Inline script inserted by a script | About 1.6 µs: the element, its insertion, the compilation and the run of a one-line script |
| Page of a 250 KB inline script, loaded | About 6.1 ms compiled, 1.5 ms read back from the script cache of the client |

The globals set up on their first use (those of the network, observer and `Intl` parts, and the interfaces of the HTML elements, `HTMLDivElement`...) are found by the first lookup of their name on the window, which inherits them: `'fetch' in window` is true, `Object.hasOwn(window, 'fetch')` false until a script assigns it. Only a read sets one up: a script that assigns one first (a polyfill, an instrumented `fetch()`) does not pay for its part. The lookup of a global that does not exist (`typeof requestIdleCallbackX`) costs a few string comparisons. The HTML elements all have the prototype of `HTMLElement`, the interface of a tag recognizing its elements by `Symbol.hasInstance`: a prototype per tag would make each property lookup on an element cross one more prototype (3 ns).

QuickJS-ng compiles about 20 MB/s of minified code and runs it within about 2 times of V8 on a first run (see the [roadmap](../ROADMAP.md#html-parsing-and-javascript-pages-aeronet_enable_html-aeronet_enable_js)). A `WebClient` keeps the bytecode of the scripts of at least 1 KiB that its pages ran, by URL and content, up to `WebClientConfig::maxScriptCacheBytes` (64 MiB, the least recently used dropped first): the same script in a later page, of any `navigate()` call, is read back instead of compiled, 15 to 70 times faster for the script itself. The external scripts and the requests of the scripts are sent one at a time.

## Limitations

- No import maps (a bare specifier fails), JSON nor CSS modules, and `<link rel="modulepreload">` is ignored (the modules are fetched when imported). An `import()` fetches its graph with the credentials of a module script without `crossorigin`, whatever the script that calls it.
- No `Blob`, `FormData`, streams (`ReadableStream`, `Response.body`), `WebSocket` nor `EventSource` for the scripts; `TextDecoder` only decodes UTF-8 (`fatal` and `ignoreBOM` supported, not `stream`).
- No layout nor rendering (see the Layout row above), no mutation records (`MutationObserver` never calls back), no `Range` (`document.createRange()`), shadow DOM, custom elements, `MessageChannel` nor `postMessage()`, and no locale data but en-US (`Intl`).
- The requests of the scripts and the external scripts are sent one at a time, without a cache (neither that of the HTTP client) nor a cache of the preflights.
